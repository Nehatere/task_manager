# Task Manager — 3-Tier AWS App

A simple task manager: add, view, update (mark done / edit), and delete tasks, with a
live-computed done/pending summary.

- **Frontend:** plain HTML/CSS/JS → deployed on **AWS Amplify**
- **Backend:** AWS **Lambda** functions behind **API Gateway**
- **Database:** **DynamoDB** (single table, partition key `taskId`)
- **Permissions:** **IAM** roles (auto-generated by SAM, scoped to just this table)

```
task-manager-aws/
├── backend/
│   ├── template.yaml       ← SAM template (defines every AWS resource)
│   └── src/
│       ├── createTask.js
│       ├── getTasks.js
│       ├── updateTask.js
│       ├── deleteTask.js
│       ├── dynamoClient.js ← shared DynamoDB client + CORS headers
│       └── package.json
└── frontend/
    ├── index.html
    ├── style.css
    ├── app.js
    └── config.js           ← paste your API URL here after deploy
```

## How a request flows (for the presentation)

1. User clicks "Add Task" in the browser (**frontend**, hosted on Amplify).
2. Browser sends a `POST` to the **API Gateway** URL with the task JSON.
3. API Gateway routes it to the **`createTask` Lambda**.
4. The Lambda validates input, builds a task object, and writes it to **DynamoDB**
   using `PutCommand`.
5. DynamoDB confirms the write; Lambda returns the created task as JSON.
6. API Gateway passes that response back to the browser; the frontend re-fetches
   the task list and re-renders.

Update/delete follow the same pattern but hit `PUT /tasks/{taskId}` or
`DELETE /tasks/{taskId}`, and IAM is what lets each Lambda's execution role
actually call DynamoDB — without it, every DynamoDB call would fail with an
`AccessDeniedException`, even though the code is "correct."

## Step 1 — Prerequisites

1. An AWS account (console access + an IAM user with programmatic access, or
   use IAM Identity Center). Free tier covers everything here.
2. Install and configure the AWS CLI:
   ```bash
   aws configure
   # enter your Access Key ID, Secret Access Key, region (e.g. ap-south-1), output format (json)
   ```
3. Install the AWS SAM CLI (used to deploy Lambda + API Gateway + DynamoDB together):
   - Mac: `brew tap aws/tap && brew install aws-sam-cli`
   - Windows/Linux: see https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html
4. Install Node.js 20+ (for local testing, and because Lambda runtime is `nodejs20.x`).

## Step 2 — Deploy the backend (Lambda + API Gateway + DynamoDB + IAM)

```bash
cd task-manager-aws/backend

# Install Lambda dependencies (SAM packages these into each function)
cd src && npm install && cd ..

# Build (SAM packages each Lambda with its dependencies)
sam build

# Deploy — the --guided flag walks you through settings the first time
sam deploy --guided
```

During `--guided` setup:
- **Stack name:** `task-manager-backend` (or anything you like)
- **AWS Region:** pick one close to you, e.g. `ap-south-1` (Mumbai)
- **Confirm changes before deploy:** Yes (good habit, lets you see what's being created)
- **Allow SAM CLI IAM role creation:** **Yes** — this is required; it's what lets SAM
  create the IAM roles your Lambdas need to talk to DynamoDB
- **Save arguments to samconfig.toml:** Yes (so future `sam deploy` needs no flags)

When it finishes, SAM prints an **Outputs** section with something like:
```
Key                 ApiUrl
Value               https://abc123xyz.execute-api.ap-south-1.amazonaws.com/prod/tasks
```
**Copy that URL** — you'll need it in Step 3.

To verify the backend works before touching the frontend:
```bash
curl -X POST <ApiUrl> \
  -H "Content-Type: application/json" \
  -d '{"title":"Test task","description":"checking the API","priority":"high"}'

curl <ApiUrl>
```
You should see your test task come back, and the DynamoDB table (`tasks-table`) should
show it if you check the AWS Console → DynamoDB → Tables → Explore items.

## Step 3 — Point the frontend at your API

Open `frontend/config.js` and replace the placeholder:
```js
const API_URL = "https://abc123xyz.execute-api.ap-south-1.amazonaws.com/prod/tasks";
```

Test locally first — just open `frontend/index.html` in a browser, or serve it:
```bash
cd frontend
python3 -m http.server 8080
# visit http://localhost:8080
```
Add a task, refresh the page, confirm it's still there — that's your three tiers
talking to each other correctly, before you even deploy the frontend.

## Step 4 — Push to GitHub

```bash
cd task-manager-aws
git init
git add .
git commit -m "Task manager: Lambda + API Gateway + DynamoDB + Amplify frontend"
git branch -M main
git remote add origin <your-empty-github-repo-url>
git push -u origin main
```
Make sure `frontend/config.js` has your real API URL committed (Amplify will serve
exactly what's in the repo).

## Step 5 — Deploy the frontend on AWS Amplify

1. AWS Console → **Amplify** → **New app** → **Host web app**.
2. Connect your GitHub account and select this repository.
3. **Important:** set the app root / monorepo path to `frontend` (since the repo
   also contains the `backend` folder). Amplify has a "monorepo" setting where you
   point it at a subdirectory.
4. Amplify auto-detects it as a static site (no build command needed for plain
   HTML/CSS/JS) — accept the defaults and deploy.
5. Amplify gives you a live URL like `https://main.xxxxxxxxxx.amplifyapp.com`.

## Step 6 — Test the full live flow

Open the Amplify URL, add a task, refresh, confirm it persists, mark one done,
delete one, and check the summary counts update. That confirms:
**Amplify (frontend) → API Gateway → Lambda → DynamoDB**, all live.

## Design notes (for the "why" questions)

- **Partition key = `taskId` (UUID), no sort key.** Each item is a self-contained
  task with no natural hierarchy or range query need, so a simple key is enough.
  A UUID avoids collisions without needing an auto-increment mechanism.
- **PAY_PER_REQUEST billing** on the table — no capacity planning needed for a
  small app like this, and it stays comfortably in the free tier.
- **Summary is calculated, not stored** — `getTasks.js` derives `done`/`pending`
  counts from the actual items on every fetch, so it can never drift out of sync
  with the real data.
- **IAM via SAM's `DynamoDBCrudPolicy`** — each Lambda gets its own scoped policy
  rather than a shared admin role, so if one function were compromised it still
  couldn't do more than read/write this one table.
- **CORS** is enabled on API Gateway and echoed in every Lambda response, since
  the frontend (Amplify domain) and backend (API Gateway domain) are different
  origins.

## Troubleshooting

- **CORS errors in browser console:** double-check `config.js` has the exact
  API URL from `sam deploy` output (including `/prod/tasks`, no trailing slash issues).
- **500 errors:** check CloudWatch Logs for the specific Lambda (Console → Lambda →
  function → Monitor → View logs) — this is the fastest way to see the real error.
- **AccessDeniedException in logs:** means the IAM policy wasn't attached — re-run
  `sam deploy` and confirm you said yes to IAM role creation.
